# Ikon AI App Development Guidelines

**Detailed API references are in docs/guides/. See the guide index at the bottom of this document.**

## Architecture

Ikon AI App is a cloud-native platform for building interactive, AI-powered multi-user experiences.

**App structure:** C# app runs in the cloud, streams reactive UI to browser clients via WebSocket. The app persists even when all clients disconnect. Multiple clients connect to the same app instance for real-time collaboration, games, and shared experiences.

**AI services (no setup required — the platform handles all API keys and connections):**
- `Emerge.Run<T>()` — LLM text generation and structured JSON output (Claude, GPT, Gemini, Grok, and more)
- `new ImageGenerator(model)` — AI image generation (Gemini, GPT Image, Flux, etc.)
- `new SpeechGenerator(model)` — text-to-speech (ElevenLabs, Azure, OpenAI, Google)
- `new SpeechRecognizer(model)` — speech-to-text (Whisper)
- `new VideoGenerator(model)`, `new EmbeddingGenerator(model)`, `new WebSearcher(model)` — other AI services

**UI system:** Declared in C# inside `UI.Root(content: view => { ... })`. The `view` parameter type is `UIView` (a class), and `IView` is a global type alias for `UIView` (defined in `GlobalUsings.cs`), so a helper can be declared with either name — `static void Render(UIView view, ...)` and `static void Render(IView view, ...)` both work. There is no `ViewContext` type, though — declaring a helper as `(ViewContext view, ...)` fails with `CS0246: type 'ViewContext' could not be found`. `UIView` provides component methods: `view.Text()`, `view.Button()`, `view.ScrollArea()`, `view.TextField()`, etc. Nested content lambdas receive their own `UIView view` parameter.

**State:** `Reactive<T>` (shared across all clients), `ClientReactive<T>` (per-client), `UserReactive<T>` (per-user). Changes automatically trigger UI updates — only the diff is streamed to clients.

**Styling:** Crosswind — Tailwind-like utility classes in C# string arrays, with a motion animation system for declarative keyframe animations (`motion-[...]`). Three layers, all valid in the same style array:

1. **Semantic theme-aware classes** (`bg-card`, `text-primary`, `bg-brand-solid`, `border-secondary`, `bg-background`) — the default path. They resolve through CSS variables that auto-flip between light and dark, and respond to per-app `IkonTheme` overrides, so light/dark mode switching and brand re-skins just work without touching individual style arrays.
2. **`Ikon.Parallax.Theming` token classes** (`Button.PrimaryMd`, `Card.Default`, `Text.H1`, `Layout.Page`, …) — pre-composed bundles of #1 above. Ergonomic shortcuts with tested defaults; use them when they fit, ignore them when they don't. They follow the theme because they're built from semantic classes.
3. **Hardcoded Tailwind palette classes** (`bg-amber-400`, `text-zinc-950`) and **raw hex** (`#1A2B3C`) — full custom control for looks that intentionally shouldn't change with the theme. These bypass the IkonTheme system entirely. The trade-off: if you later add light/dark switching or a brand re-skin, every fixed-color site needs to be revisited.

The three compose freely in the same array (`[Button.PrimaryMd, "mt-4 self-center"]`, `["bg-card border border-secondary p-6 rounded-2xl"]`).

**Theming:** Per-app brand commitment goes in `new IkonTheme { ["primary"] = "amber-400", ["background"] = "zinc-950", ... }` at the `UI` initializer — an indexer-keyed object initializer where each entry sets one CSS variable. There are NO named init properties (no `Brand =`, no `Background =`) and NO auto-fan-out. The platform `IkonTheme` (in `Ikon.Parallax.Theming`) is the only configurable surface — there is no local `IkonTheme.cs` to edit. See the **Ikon Theming Guide** in `docs/guides/ikon-theming-guide.md` for the canonical reference (palette/font/radius/motion overrides, dark-mode pairing, palette-from-image workflow).

**Audio:** `private Audio Audio { get; } = new(app);` — audio synthesis (Ikon.Resonance), effects, playback, and client microphone/camera capture.

**Namespaces:** All Ikon namespaces are auto-imported via `GlobalUsings.cs` — no manual `using` statements needed for Ikon types.

## Development Focus

- Most development happens in the C# app, including styling
- LLM text generation uses `Emerge.Run<T>()`. Other AI services (image, speech, video) are standalone classes instantiated directly
- UI is declared inside `UI.Root([Page.Default], content: view => { ... })` — components are methods on the `view` lambda parameter
- Crosswind styling: Tailwind-like syntax in style arrays, with motion animation system
- `Reactive<T>` for shared state, `ClientReactive<T>` for per-client state — changes trigger UI updates automatically
- All Ikon namespaces are auto-imported via `GlobalUsings.cs`
- Only modify frontend-node when integrating custom React UI components
- Developers can freely add any NuGet packages to C# app or npm packages to frontend

## Common Pitfalls

These are the recurring hallucination + footgun classes seen across generated Ikon apps. Each one compiles or runs cleanly in the wrong shape and silently breaks the app — read this list before writing UI code.

- **Reactive UI re-render is implicit. There is NO `view.Dynamic`, `view.Watch`, `view.Bind`, `view.Observe`, `view.When`, `view.Live`, `view.Reactive`, or any other wrapper component for reactive rendering.** When you read `_x.Value` inside a UI lambda (e.g. `view.Text([…], _name.Value)` or `if (_open.Value) { view.Box(…); }`), the framework records that dependency and automatically re-renders the enclosing subtree on change. Just read `.Value` directly. Inventing `view.Dynamic(reactive, content: view => …)` causes CS1061 ("UIView does not contain a definition for Dynamic").
- **`Emerge` is a static class, not an injected service.** Call `Emerge.AskAsync(prompt)` or `Emerge.Run<T>(model, ctx, pass => …)` directly. There is no `IEmerge`, no `app.Services.GetRequiredService<IEmerge>()`, no constructor-injection pattern. The same goes for `Audio`, `UI`, and other helper handles — `Audio` is `new(app)` in the app class, not service-resolved.
- **Not every view component takes `props:`.** `view.Text`, `view.Button`, `view.Box`, `view.Image` and most input/display components accept `props:` for HTML attributes. `view.Column`, `view.Row`, `view.Grid` and pure layout primitives do NOT — `style:` / `styleId:` / `key:` / `content:` only. Passing `props:` to a layout primitive produces CS1739.
- **`LLMModel` has NO `Default` value.** Canonical enum values include `Claude46Sonnet`, `Claude45Sonnet`, `Claude45Haiku`, `Gemini25Flash`, `Gemini25Pro`, `Gpt5Mini`, `Gpt5`, `Grok420Reasoning`. Pick a specific model per `Emerge.Run<T>(LLMModel.X, …)` call. `LLMModel.Default` produces CS0117 — default to `Claude46Sonnet` for general chat / reasoning, `Claude45Haiku` for fast cheap text.
- **AI-service results are NULLABLE — null-guard them before use, or the build fails with CS8602** ("dereference of a possibly null reference"; the build runs warnings-as-errors). An AI call can fail or return nothing, so guard the result before dereferencing it. The standalone generators return genuinely nullable results — the static `ImageGenerator.GenerateAsync(prompt)` returns `ImageGeneratorResult?`, and likewise `VideoGenerator`, `SpeechGenerator`, etc. produce nullable/optional results — so dereferencing one without a guard fails the build with CS8602. `Emerge.Run<T>(…).FinalAsync()` returns `(T result, KernelContext context)`: the result is non-nullable in the signature, but generation can still fail, so guard it defensively too. Guard once, right after the call, then use the non-null value: `var (recipe, ctx) = await Emerge.Run<Recipe>(…).FinalAsync(); if (recipe is null) { _error.Value = "Generation failed"; return; }` and `var img = await ImageGenerator.GenerateAsync(prompt); if (img is null) { return; } view.Image([…], data: img.Data, mimeType: img.MimeType);`. Use `?.`/`??` when reading into the UI from reactive state (`card.Recipe?.Title ?? "Untitled"`). Do NOT dereference the raw result (`recipe.Title`, `img.Data`) without a guard. (The streaming form's `Completed<T>.Result` inside `if (ev is Completed<T> c)` is the value for that case — handle the non-`Completed` events too.)
- **`Emerge.Run<T>` takes THREE args — `(LLMModel model, KernelContext context, Action<EmergePass<T>> configure)` — and returns an `IAsyncEnumerable<EmergeEvent<T>>`, NOT the result. The prompt is NOT a positional arg; it goes in the configure lambda as `pass.Command`.** Two shapes go wrong, both seen repeatedly: (a) passing a bare prompt string — `Emerge.Run<T>(LLMModel.X, prompt)` — is **CS1501** "no overload for method 'Run' takes 2 arguments"; (b) deconstructing the stream without `.FinalAsync()` — `var (result, _) = await Emerge.Run<T>(…)` — is **CS8130** ("cannot infer the type of implicitly-typed deconstruction variable") + **CS8183** ("implicitly-typed discard"). Copy this canonical one-shot call whole — every piece (the three args, `pass.Command`, `.FinalAsync()`, the null guard) is load-bearing: `var (result, ctx) = await Emerge.Run<MyResult>(LLMModel.Claude46Sonnet, new KernelContext(), pass => { pass.Command = userPrompt; }).FinalAsync(); if (result is null) { _error.Value = "Generation failed"; return; }`. The streaming form keeps the same three args but iterates instead of `.FinalAsync()`: `await foreach (var ev in Emerge.Run<T>(LLMModel.X, new KernelContext(), pass => { pass.Command = userPrompt; })) { … }`.
- **`Emerge.AskAsync` is PROMPT-FIRST — `AskAsync(string command, LLMModel model = …)` — the OPPOSITE order from `Emerge.Run<T>(LLMModel model, …)`.** Carrying the `Run<T>` "model first" shape over to `AskAsync` — `Emerge.AskAsync(LLMModel.Claude46Sonnet, prompt)` — is **CS1503** (×16 in one app, and it blanks the app): the model lands in the `string command` slot and the prompt in the `CancellationToken` slot. Correct: `await Emerge.AskAsync(userPrompt)` or, to pick a model, `await Emerge.AskAsync(userPrompt, LLMModel.Claude46Sonnet)`. `AskAsync` returns a plain `string` — for structured/typed JSON use `Emerge.Run<T>` instead.
- **`onSubmit:` and `onClick:` lambdas that contain `await` must be `async`.** Writing `onSubmit: text => { return; }` inside a `Func<string, Task>` produces CS0126 and CS1643. Use `onSubmit: async text => { await SendAsync(); }`.
- **`autoScrollKey:` on `view.ScrollArea` is `string?`, not a Reactive or list.** Pass a string that changes when content changes: `autoScrollKey: _messages.Value.Count.ToString()`. Passing a `Reactive<List<…>>` produces CS1503.
- **`view.TextField` has TWO overloads — never mix positional + named args.** Overload A starts `(view, Reactive<string> bind, style, …)`; Overload B starts `(view, style, value, …)`. Writing `view.TextField(["flex-1"], bind: _input, …)` makes C# pick overload A (because `bind:` exists only there), and the positional `["flex-1"]` falls into the `Reactive<string>` slot → CS1744. Use ALL named arguments: `view.TextField(bind: _input, style: ["flex-1"], onSubmit: async t => …)`. Same caution applies to any component with multiple positional-first overloads — when in doubt, name everything. **The editable-binding parameter is `bind:` (a `Reactive<string>`) — NOT `value:`.** The web-form reflex `view.TextField(value: _input.Value, …)` is **CS1739** "no parameter named value" (and even when an overload accepts it, it would be one-way and drop edits); for any field the user types into, bind a `Reactive<string>` with `bind:`.
- **TextField `disabled:` must NOT be bound to fast-changing reactive state.** Binding `disabled: _busy.Value` or `disabled: _phase.Value != null` re-mounts the input on every flip and drops keyboard focus mid-typing — the textbox becomes unusable. Static `disabled: true` for read-only fields is fine. To gate a submit during async work: leave the TextField enabled, gate the action on the Button (`disabled: _busy.Value`) and early-return in the submit handler.
- **`onClick:` is `Func<Task>?` — ALWAYS write it `async`.** Every clickable component's `onClick:` (including `view.Box`, `view.Button`, `view.Image`) takes a `Func<Task>`, so the lambda must return a `Task`. The non-async forms all FAIL: `onClick: () => _foo.Value = x` binds as an expression lambda returning the assigned value (CS0029/runtime); `onClick: () => { _foo.Value = x; }` is a void-body statement lambda that can't convert to `Func<Task>` (**CS1643** "not all code paths return a value"). The ONLY correct shape is `onClick: async () => { _foo.Value = x; }` — keep it `async` even when the body has no `await`. (`view.Box` DOES accept `onClick:` for a clickable container — it's `Func<Task>?` like the rest.)
- **Only `view.Box`, `view.Button`, `view.Image`, and `view.Link` take `onClick:`. `view.Text` and the layout primitives (`view.Row`, `view.Column`, `view.Grid`) do NOT** — passing `onClick:` to them is **CS1739** ("no parameter named onClick"). The HTML/React prior "any element can be clickable" does not hold here. To make a piece of text clickable (e.g. a sortable column header), wrap it: `view.Box([…], onClick: async () => { … }, content: v => v.Text([…], "Label"))`, or use `view.Button([…], onClick: async () => { … }, content: v => v.Text([…], "Label"))` when it should read as a button (see the `sortable-list-header` pattern).
- **`view.Button`: style[] first positional, everything else named** (the one shape from the rule above): `view.Button(["px-4 py-2"], label: "Save", onClick: async () => { … })`. The footgun is a POSITIONAL second argument: `view.Button("Save", async () => { … })` puts the lambda into the `style[]` slot (Button's text-first overload's 2nd positional parameter is `style`, not `onClick`) → CS1744 / CS1503. Pass the label as `label:` named, never as a leading positional string.
- **Copy / share / download are declarative `view.ActionButton` actions — NOT imperative `ClientFunctions` calls.** To copy text to the clipboard: `view.ActionButton([…], action: ActionKind.CopyToClipboard, options: new CopyToClipboardActionOptions { Text = theText }, content: v => v.Icon([Icon.Sm], name: "clipboard-copy"))`. There is NO `ClientFunctions.CopyToClipboardAsync`, no `ClientFunctions.RunJavaScriptAsync`, and no clipboard method on `ClientFunctions` at all — inventing one is **CS0117** ("ClientFunctions does not contain a definition for CopyToClipboardAsync"). The "call a clipboard API on the client" prior is wrong; these run client-side with no server round-trip. Same shape for `ActionKind.Share` (`ShareActionOptions { Title, Text }`) and `ActionKind.DownloadFile`. **To show a notification, do NOT use an ActionButton** — notifications are server-initiated via `app.Notifications` (see the **Notifications** guide), not a client action. **`DownloadFileActionOptions` takes `Data` (a `byte[]`, NOT a string) and `Filename` (lowercase `n` — NOT `FileName`, NOT `Name`):** `new DownloadFileActionOptions { Filename = "notes.md", Data = System.Text.Encoding.UTF8.GetBytes(text) }` — any other property name is **CS0117**. (See the `copy-and-share-action-row` pattern.)
- **`ScrollArea`: bare `style:` styles the outer wrapper (same as `rootStyle:`); `viewportStyle:` styles the scrollable content area.** Both work as positional or named — `view.ScrollArea(["flex-1 min-h-0"], viewportStyle: ["px-4"], content: …)` is the common shape. If padding seems wrong, you probably meant `viewportStyle:` instead of `style:`.
- **`AudioContainer` carries PCM samples, not encoded bytes.** Properties are `float[] Samples`, `int SampleRate`, `int ChannelCount` — there is no `.Data` / `.MimeType`. To play `SpeechGenerator` output: declare `private Audio Audio { get; } = new(app);` then `Audio.SendSpeech(audio)` per chunk in the `await foreach`. `ClientFunctions.PlaySoundAsync(byte[], string)` is a different API for already-encoded MP3/WAV blobs.
- **Audio is synthesized SERVER-side and streamed to clients — there is NO browser Web Audio API, no client-side JavaScript synthesis, and no custom React component needed to make sound.** To play tones, drum hits, beeps, or any synthesized sound: build the PCM `float[] samples` server-side (hand-fill a `float[]` with a sine/decay envelope, or use `Ikon.Resonance.Synth` oscillators/filters/envelopes) and stream them with `private Audio Audio { get; } = new(app);` then `await Audio.SendAsync(samples, sampleRate, channelCount, isFirst: true, isLast: true, streamId: id)`. Do NOT reach for `ClientFunctions` to inject/run JavaScript, a `view.CustomComponent` wrapping the Web Audio API, or an `AudioContext` in the frontend — those are the web-dev reflex and are not how Ikon plays sound. (`ClientFunctions.PlaySoundAsync(byte[], mimeType)` exists only for an already-encoded MP3/WAV blob, not for synthesis.) See the audio-video guide for the synthesis + `Audio.SendAsync` pattern.
- **`WebSearcher` uses `SearchPagesAsync(SearchConfig)`, not a positional `SearchAsync(string, int)`.** Real shape: `await searcher.SearchPagesAsync(new SearchConfig { Query = q, MaxResults = 5 });`. `SearchResult` exposes `Url`, `Title`, `Content`, `Mimetype`, `Keywords` — there is no `Snippet`; use `result.Content` for the body text.
- **`view.Image`'s first positional arg is the style array (like every other component) — `src` / `data` are NAMED.** The shapes are `view.Image(["w-72 h-72 rounded"], src: url, alt: "…")` for a URL and `view.Image(["w-72 h-72"], data: bytes, mimeType: "image/png", alt: "…")` for raw bytes. Do NOT write `view.Image(url, ["w-72"], …)` — that puts the URL in the `string[] style` slot (CS1503) and the style array in the `string? src` slot (CS1739/CS0029). There is no `classes:` parameter. Style FIRST, source NAMED.
- **A custom frontend node — `view.AddNode(type: "x.y", …)` — renders BLANK unless a React resolver for `"x.y"` is registered in `frontend-node/src/app.tsx`. This is the most dangerous trap in the framework because NOTHING in the build catches it:** the C# compiles and the Critic scores it 9/10 (both only see C#); only at runtime does the browser log `[UIRenderer] No renderer for node type x.y` with a blank area where your component should be. A working custom component needs ALL FOUR parts together — a React component, a resolver, `registerModule(...)` in `app.tsx`, and the C# `AddNode` extension. **So do NOT reach for `view.AddNode` / custom node types by default.** Build everything you can from native `view.*` components first. For a chart / diagram / visual that native components don't cover, render it SERVER-SIDE to SVG or PNG and display it with `view.Image([…], data: bytes, mimeType: "image/svg+xml")` — zero frontend code, can't go blank. **Strongly avoid hand-building a custom React component in this flow — it reliably spirals** (the C# `AddNode` plumbing and the React resolver + `registerModule` registration must all line up, and a partial attempt — an orphan resolver file that isn't registered, or a registered module without the C# extension — STILL renders blank). Even for a "genuinely interactive" surface like a freehand sketchpad or whiteboard, do NOT reach for `view.AddNode`: instead implement the closest experience from native `view.*` components, or render a server-side SVG/PNG snapshot via `view.Image(...)`, accepting reduced live-interactivity. A correct, fully-rendered simpler app beats a blank "perfect" one. (If a custom component is truly unavoidable, `guide("custom UI component — React resolver + registerModule in app.tsx + AddNode C# extension")` first and write ALL four parts — but expect the build's frontend-renderer gate to reject any custom node type whose resolver isn't registered.) Never emit a custom node type and assume it renders.
- **EXCEPTION — real-time MULTI-USER (collaborative editing, multiplayer games with local rendering) is the ONE case where a custom React canvas + a custom Teleport `.tp` message is the RIGHT tool, not native components.** When the brief needs many clients to see each other's high-frequency actions live — a shared whiteboard where everyone sees strokes appear, a multiplayer game with moving players, live cursors — native `view.*` and server-side SVG snapshots cannot express it (they have no client→client live channel). For a per-frame REAL-TIME game (snake, agar/arena, anything with a game loop) this is also a PERFORMANCE requirement: driving the playfield through Parallax `Reactive` state streams a UI diff on every tick, which is too slow and floods the channel — stream the game state over the `.tp` transport and render each frame LOCALLY on the custom canvas instead, keeping only the lobby/score/controls in native `view.*`. The deliberate, validated pattern: (a) declare a `schema/<Name>.tp` message type (add `unreliable = true` for drop-tolerant high-frequency streams like positions/strokes); (b) build the four-part custom canvas component that sends/receives it via the SDK `appMessaging` helper (`appMessaging(client).send(Type, value)` / `.on(Type, handler)`); (c) on the server, `app.OnMessage<T>((payload, senderId) => …)` to receive and `app.SendMessageAsync(payload, targetIds)` to fan out — the **app is the router** (decide recipients explicitly; the server never auto-broadcasts app-local messages). EXACT arg counts (codegen reliably gets these wrong → CS1501/CS1955): `OnMessage<T>` takes ONE arg, the handler `(payload, senderId)` — NO message-name string; `SendMessageAsync` takes TWO args, message + targets (`app.Clients.Ids.ToList()` or a single `int` session id) — type inferred, so NO name string and NO 4th arg; `app.BackgroundWork` is a PROPERTY not a method — run a tick loop with `_ = Task.Run(async () => { while (running) { Tick(); await app.SendMessageAsync(Snapshot(), app.Clients.Ids.ToList()); await Task.Delay(100); } })`, never `app.BackgroundWork(...)`; the `schema/<Name>.tp` sits at the app root and generates `app/<App>/Generated/Protocol/<Name>.cs` — reference the type (e.g. `GameState`) directly, no using. Keep everything that ISN'T the live shared surface — toolbars, scoreboards, side panels — in native `view.*` reactive components; ONLY the high-frequency shared surface goes custom. **The exact trap (it compiles and runs, so nothing flags it): mounting a custom canvas but feeding it per-tick state via `view.AddNode` props sourced from a server `Reactive`.** A "custom `.tp` component" is NOT a custom *component* — `.tp` is the Teleport MESSAGE PROTOCOL, not the component file. WRONG: `Reactive<GameState> _game` + `view.AddNode("custom.board", new(){ ["stateJson"]=JsonSerialize(_game.Value) })` pushed every tick (routes per-frame state through the UI-diff pipeline). RIGHT: a `schema/<Game>State.tp` type; the tick loop calls `app.SendMessageAsync(state, app.Clients.Ids.ToList())`; the canvas subscribes via `appMessaging(client).on(StateType, render)` and draws on its own `<canvas>`; input returns via `appMessaging(...).send(...)` → `app.OnMessage<Input>`. `AddNode` mounts the canvas ONCE for layout — it is NOT the per-tick data channel. If your plan has `AddNode` props that change each tick, or a `Reactive` holding live game state, you're on the slow path. Reference app: **Ikon.App.Arena** (a real-time multiplayer arena game — the canonical custom-.tp app). `guide("real-time multi-user custom .tp app — schema/*.tp + appMessaging + custom canvas + server router")` for the complete end-to-end pattern before writing it.
- **Real-time-multiuser footguns (both seen in generated apps — and the codegen build gate now compiles the frontend too, so a broken import FAILS the build instead of silently shipping):** (1) **Import paths** — `appMessaging` comes from `@ikonai/sdk`; custom-UI renderer types (`UiComponentRendererProps`, `useUiNode`, `IkonUiComponentResolver`, `IkonUiModuleLoader`, `IkonUiRegistry`) from `@ikonai/sdk-react-ui`; the generated codecs (`toProtocolMessageX`, `fromProtocolMessageX`, `X_OPCODE`) from `'../generated/protocol/<name>'`. There is **NO `@ikonai/sdk-react`** package — importing from it fails the frontend build. (2) **Use the TYPED server API, not the untyped passthrough** — receive with `app.OnMessage<Stroke>(async (payload, senderId) => …)` and fan out with `app.SendMessageAsync(payload, targetIds)` to the recipients YOU choose (e.g. `app.Clients.Ids.Where(id => id != senderId && id != app.ClientContext.SessionId).ToList()`). Do **NOT** write `app.OnMessageReceived(async msg => await app.SendMessageAsync(msg))` — that untyped passthrough blindly re-broadcasts the raw message with no typing, no chosen recipients, and no late-join, which is not the server-as-router model. (3) **Inside the custom canvas component, get the client from the renderer props — NEVER `useIkonApp()`.** The renderer's props are `{ nodeId, context, className }: UiComponentRendererProps`; obtain the live client with `const client = context.client;` and the node (for mount-time props) with `const node = useUiNode(context.store, nodeId);`. Calling `useIkonApp()` inside a node component throws at runtime — **`TypeError: Cannot destructure property 'authConfig' of 'options'`** — because `useIkonApp` is the APP-SHELL hook (used once in `app.tsx` with an authConfig), not a per-node hook. The frontend build compiles either way, so the build does NOT catch this — only the running app crashes with a blank canvas. Then `appMessaging(client).on(SnapshotMsg, …)` / `.send(InputMsg, …)` — where `SnapshotMsg`/`InputMsg` are **`AppMessageType<T>` descriptors** (imported `AppMessageType` from `@ikonai/sdk`) built from the GENERATED codec: `const SnapshotMsg: AppMessageType<GameSnapshot> = { opcode: GAME_SNAPSHOT_OPCODE, toProtocolMessage: toProtocolMessageGameSnapshot, fromProtocolMessage: fromProtocolMessageGameSnapshotAsync };` (those three come from `'../generated/protocol/game-snapshot'`). **Do NOT pass a string opcode name** (`messaging.on('GAME_SNAPSHOT', …)`) or the bare interface — a string makes `.on()` silently never fire, so the canvas renders but no state arrives ("Connecting…" forever) and nothing in the build catches it. Unsubscribe with `sub.close()` (not `.unsubscribe()`). Mirror Ikon.App.Arena's `arena-canvas.tsx`.
- **For SINGLE-USER freehand drawing / sketch / image-annotation apps, use the NATIVE `view.ImageEditorCanvas` — do NOT hand-build a custom canvas component.** (For a MULTI-user live-shared drawing surface, that's the real-time-multiuser exception above — `ImageEditorCanvas` is a single-user annotator and has no client→client sync.) It's a built-in drawing surface with its renderer already registered, so it just works. Validated shape: `view.ImageEditorCanvas(style: ["w-full h-full min-h-[500px]"], src: optionalImageUrl, brushColor: _color.Value, brushWidth: _size.Value, tool: _tool.Value /* "brush" | "eraser" | "text" */, onSave: async args => { /* args holds the edited image */ }, onHistoryChange: async args => { _canUndo.Value = args.CanUndo; _canRedo.Value = args.CanRedo; })`. Undo / redo / save are fired by **bumping integer counter props** — `triggerUndo:` / `triggerRedo:` / `triggerSave:` each take an `int?`; increment a `Reactive<int>` and pass `.Value` to trigger the action (there is no `Undo()` method to call).
- **File upload: the simplest correct flow is accept-then-complete; the callbacks' `AssetUri` is a `string?`, NOT the `AssetUri` struct.** `view.FileUpload(accept: ["image/*"], onUploadComplete: async args => { … })` — the simplest accept is to **OMIT `onUploadStart` entirely** (auto-accept), then read the finished upload in `onUploadComplete` where `args.AssetUri` (a URI **string**) and `args.LocalTempFilePath` are available. If you DO supply `onUploadStart`, its return type is `Task<FileUploadStartResult>` (NOT `Task<bool>`): write `onUploadStart: async args => true` (a `bool` implicitly converts to `FileUploadStartResult` and `async` lifts it into the `Task`) — do NOT write `onUploadStart: args => Task.FromResult(true)`, which infers `Task<bool>` and fails with **CS0029**. To pre-route the bytes into the asset system, `onUploadStart: async args => new FileUploadStartResult(assetUriString)`. Store the result in `Reactive<string?>` (the URI string) — NOT `Reactive<AssetUri?>`; the `AssetUri` struct is a different type used by the `Asset` API (`new AssetUri(str)`), and assigning the callback's `string?` to it is CS0029. When you later read the asset back, every `Asset.Instance.*` op (`GetMetadataAsync`, `GetBytesAsync`, `SetBytesAsync`, …) takes the **`AssetUri` struct**, so wrap the stored URI string and null-guard first: `if (uri is null) return; var bytes = await Asset.Instance.GetBytesAsync(new AssetUri(uri));` — passing the raw `string?` is **CS1503**. To unwrap a genuine `AssetUri?` (nullable struct) use `.Value` after a null check, never the `!` operator (which only suppresses reference-type warnings).
- **Field initializers cannot reference OTHER instance members — no other fields, no `this`.** (The primary-constructor `app` parameter IS in scope and is fine in an initializer — that's exactly how `private Audio Audio { get; } = new(app);` works — but reading another instance field is not.) Writing `private readonly Action _wire = () => { _hostId.Value = …; };` or any field initializer that touches another instance field produces **CS0236** "a field initializer cannot reference the non-static field, method, or property". Reactive fields init with a literal default only (`new(0)`, `new([])`). Put anything that reads other instance fields — and event wiring like `app.OnClientJoined(...)` — inside `Main()` or a method, never a field initializer.
- **Database access: open a connection PER-OPERATION via a helper method — do NOT hold one as a field.** `AppDatabaseConnection` is a STATIC class, so a field of it (`private AppDatabaseConnection _db;`) is **CS0723** "cannot declare a variable of static type", and even a `DbConnection` field initialized from `app` (`private readonly DbConnection _conn = AppDatabaseConnection.Create(app, "db");`) — while it compiles — is wrong, because a single long-lived connection breaks under concurrent handlers. The ASP.NET/EF "inject a long-lived DbContext field" prior does NOT apply here. `AppDatabaseConnection.Create(app, "name")` returns a fresh ADO.NET `DbConnection` you open and dispose per use. Canonical pattern: `private DbConnection OpenConn() => AppDatabaseConnection.Create(app, "contactsdb");` then in each method `await using var conn = OpenConn(); await using var cmd = conn.CreateCommand(); cmd.CommandText = "..."; …`. Ensure the table exists once in an `app.OnStarting(...)` handler (a `CREATE TABLE IF NOT EXISTS`). For anything past a single flat table, prefer **EF Core** — the same per-operation rule applies to the `DbContext` (build a fresh one from `app.Databases.First(d => d.Name == "X").ConnectionString` inside each method, never a long-lived field), and apply migrations with `await db.Database.MigrateAsync()` in `app.OnStarting(...)`. Raw `DbConnection` + SQL is the lightweight option for a table or two; see the databases guide for the EF Core setup. Either way, using a database `"X"` requires `"X:postgres"` under `Databases` in `ikon-config.development.toml`.
- **Runtime-computed percentage widths (`w-[{pct}%]`) do NOT work — Crosswind only generates classes it can see in source at build time, so a string-interpolated class never exists.** Static fraction widths like `w-1/2`, `w-3/10`, `w-7/12` all work (any `n/d` resolves to a percent) and arbitrary literals like `w-[30%]` also work. But for a **runtime-computed** percentage (e.g. a data-driven bar/progress width) set it inline instead: `view.Box(["h-2 bg-sky-500"], props: new Dictionary<string, object> { ["style"] = $"width: {pct}%" })`.
- **`props:` MUST be constructed as `new Dictionary<string, object> { … }` — NEVER target-typed `new() { … }`.** The `props:` parameter is typed `IReadOnlyDictionary<string, object>?`, so a target-typed `props: new() { ["style"] = "…" }` infers the INTERFACE as the type to create, which fails TWO ways at once (the single most common pair of errors in generated apps — ~25 of each in one app): **CS0144** "Cannot create an instance of the abstract type or interface 'IReadOnlyDictionary<string, object>'" (you can't `new` an interface) AND **CS0200** "Property or indexer 'IReadOnlyDictionary<string, object>.this[string]' cannot be assigned to — it is read-only" (the interface's indexer has no setter). Always name the concrete type: `props: new Dictionary<string, object> { ["style"] = $"width: {pct}%", ["title"] = "Tooltip" }`. Same rule anywhere a `props:` / HTML-attributes dictionary is passed.
- **NEVER add `using Ikon.*;` directives — every Ikon namespace is already imported via `GlobalUsings.cs`.** Just write the type name (`WebSearcher`, `Emerge`, `Audio`, …). Inventing an import for a feature you're about to use — `using Ikon.Agent.WebSearch;`, `using Ikon.Agent;`, `using Ikon.WebSearching;` — produces **CS0234** "namespace does not exist in the namespace 'Ikon'" because those namespaces are made up. The real namespaces (e.g. `Ikon.AI.WebSearching`) are ALL already in the global usings; you never need a per-file `using` for an Ikon type. **This rule applies ONLY to Ikon namespaces.** A third-party NuGet package you add (e.g. `QRCoder`, `Markdig`) is NOT in GlobalUsings — it still needs its own `using QRCoder;` / `using Markdig;`, or its types fail with CS0246/CS0103.
- **`MessageAuthor` value comparison uses the static instances, not the nested types.** `Author == MessageAuthor.User` works (User is a static `MessageAuthor` instance). `Author == MessageAuthor.UserAuthor` does NOT compile — `UserAuthor` is a nested record type, not a value. For type-pattern matching use `is`: `Author is MessageAuthor.UserAuthor`. Same for `System` / `SystemAuthor`, `Agent(name)` / `AgentAuthor`, `Thread(id)` / `ThreadAuthor`.
- **`Reactive<List<T>>` collection mutation must go through the extensions, not `.Value.Add(...)`.** `_items.Add(x)` mutates and notifies in one call. `_items.Value.Add(x)` mutates the underlying list without firing the change event — UI doesn't refresh. Same for `Remove`, `Clear`, `RemoveAt`, `Insert`, `RemoveAll`.
- **`Reactive<T>` / `ClientReactive<T>` / `PersistentReactive<T>` / `PersistentUserReactive<T>` / `PersistentSessionReactive<T>` are `private readonly` FIELDS initialized with `new(defaultValue)` — ONE positional arg.** They derive their storage key from the field name via `[CallerFilePath]` / `[CallerMemberName]` — pass NOTHING else. RIGHT: `private readonly ClientReactive<int> _count = new(0);`, `private readonly PersistentUserReactive<List<TodoItem>> _todos = new([]);`. WRONG (all produce CS1503 / CS7036 build errors): `new ClientReactive<int>(app, 0)` — IApp is NOT a ctor arg; `app.ClientReactive<int>(0)` / `view.ClientReactive(0)` — there is NO such method on IApp or UIView; `new PersistentUserReactive<T>("key", default)` — there is no key arg. The ASP.NET / EF Core mental models (`context.Get<T>("key")` or `new(context, "key", default)`) do not apply to Ikon reactives. **For the default value, give an explicitly-typed value or a collection expression — never a bare target-typed `new()`.** `new([])` for an empty list is fine, but `new PersistentReactive<Dictionary<int, Player>>(new())` is **CS0121 ambiguous**: the inner `new()` matches both the `(T value)` ctor and an internal `(UseDefault)` ctor overload. Write the value explicitly: `new(new Dictionary<int, Player>())`, `new([])` (list/array), `new("")`, `new(0)`.
- **`UIView` is a component-rendering surface only — it has NO methods for creating or subscribing to reactive state.** `view.ClientReactive(...)`, `view.Reactive(reactive, lambda)`, `view.Persistent(...)`, `view.Watch(...)`, `view.Bind(...)` ALL fail with CS1061. Reactive state is declared at class level (see field-init pitfall above), and subscription is implicit — reading `.Value` inside a UI lambda registers the dependency. There is no view-side "reactive scope" API.
- **Per-client state is implicit — `ClientReactive<T>.Value` auto-resolves to the CURRENT client. Do NOT fetch a client id and look the value up manually.** There is no `view.ClientContext`, no `view.ClientSessionId`, and no `_x.Get(clientId)` / `_x.For(clientId)` accessor on `ClientReactive<T>` — all produce CS1061. Inside any UI lambda or `onClick`/`onSubmit`/`onValueChange` handler, just read and write `_x.Value`; the framework scopes it to the client that's rendering or that fired the event. The web-session mental model ("get the session id, then index per-session state") does NOT apply — a handler that needs per-client behavior takes no `clientId` parameter. (If you genuinely need the joining client's identity in a lifecycle handler, that's `app.OnClientJoined(async ctx => …)` with `ctx.ClientSessionId` — but that is the `Context`, not anything on `view`.) **Client/session ids are `int`, never `string`:** `ReactiveScope.ClientId` is `int`, `ctx.ClientSessionId` is `int`, `ReactiveScope.ClientIdOrNull` is `int?`, and `app.Clients[id]` is indexed by `int`. Type any client-id local, method parameter, or reactive as `int` / `int?` (e.g. `Reactive<int?> _hostId`, `void StartTimer(int clientId)`) — a `string clientId` param or `Reactive<string>` host-id state produces CS1503/CS0266 the moment you assign `ReactiveScope.ClientId` to it. **Writing `ClientReactive<T>` from a BACKGROUND / async task — a `Task.Run` tick loop, an animation/simulation loop, anything running after the original UI callback returned — loses the implicit client scope, so the write silently goes to the wrong place or no-ops.** Re-establish the scope around the write: `using (ReactiveScope.Use(new ClientScope(clientSessionId))) { _clientReactive.Value = …; }`. **`ReactiveScope.Use` takes an `IScopeKey` — pass `new ClientScope(id)`, NEVER the bare int id** (`ReactiveScope.Use(clientId)` → **CS1503** "cannot convert from 'int' to 'IScopeKey'") and **never a lambda** (`ReactiveScope.Use(() => …)` → **CS1660** "cannot convert lambda to 'IScopeKey'"). Capture the id BEFORE you start the background task (`var cid = ReactiveScope.ClientId;` inside the triggering callback, or `ctx.ClientSessionId`), because `ReactiveScope.ClientId` is not available off the UI thread. (Plain shared `Reactive<T>` needs none of this — only `ClientReactive<T>`/`UserReactive<T>` writes from a background task do.) The method is **`ReactiveScope.Use(...)`** (returns an `IDisposable`) — there is NO `ReactiveScope.Open` / `.Enter` / `.Begin` / `.Push` (inventing one is **CS0117** "ReactiveScope does not contain a definition for 'Open'").
- **`Cells` is an ADVANCED, rarely-needed API — do NOT reach for it by default, and never invent members on it.** The recurring failure: an app guesses `Ikon.App.Cells.Initialize(...)` / `Ikon.App.Cells.Current` (→ **CS0234** "the type or namespace name 'Initialize' does not exist in the namespace 'Ikon.App.Cells'") to hold shared/global state. Those do NOT exist — the platform initializes cells itself at startup. For cross-CLIENT shared state (a global counter, a shared list everyone sees), just use a plain **`Reactive<T>`** field (it's shared across all clients in the app instance already); for durable state use `PersistentReactive<T>`. A `[Cell]` (reached via `Cells.Connect<IFoo>(new SessionIdentity(roomId))`) is ONLY for state that must be shared by a KEY across otherwise-isolated per-user app instances (e.g. a chat room keyed by room id). If the brief is a normal single-instance app, you do not need `Cells` at all — reach for it only when the plan explicitly calls for per-key cross-user rooms.
- **Blank white / empty screen at runtime (build is clean, but the page shows nothing — the visual gate scores it 0/10 and you spiral re-styling components that aren't the problem).** Check these THREE causes FIRST, in order: (1) **the root doesn't fill the viewport** — wrap the whole UI in a full-height root: `UI.Root([Page.Default], content: view => { view.Column(["min-h-screen w-full …"], …); })`. Do NOT rely on arbitrary `h-[100dvh]` / `h-screen` on a bare inner div (Crosswind may not emit an unused arbitrary class, and without a height chain the content collapses to nothing). (2) **the page background/text is white-on-white or nothing is painted** — commit a theme (`new IkonTheme { ["background"]=…, ["text-primary"]=… }`) and put content on a `bg-background`/`bg-card` surface; don't leave the default white page with no painted content. (3) **a custom `view.AddNode(...)` whose React resolver isn't registered renders blank** — use native `view.*` or a server-rendered `view.Image(...)` instead. If a build-clean app looks empty, fix the ROOT/height/background first — do not re-style individual cards chasing it.
- **THE ONE `view.*` call shape — use it for EVERY component, no exceptions: the `style` `string[]` is the ONLY positional argument; pass it bare and FIRST; name EVERY other argument (`content:`, `text:`, `label:`, `onClick:`, `props:`, `key:`, …).** This is the single most common spiral in generated apps (CS1744 + CS8323, seen 18-20× in ONE app). There is exactly ONE valid shape — do not give yourself alternatives to mix: `view.Column(["flex gap-4"], content: v => …)`, `view.Text(["text-lg"], text: "Hi")`, `view.Button(["px-4 py-2"], label: "Save", onClick: async () => …)`. **The display-string parameter is `text:` on `view.Text` and `label:` on `view.Button` — NOT `value:`** (writing `view.Text([…], value: "Hi")` is **CS1739** "no parameter named value", seen 24× in one app). Both recurring errors come from breaking it: (a) ALSO writing `style:` when the array is already positional — `view.Column(["flex gap-4"], style: "p-4")` → **CS1744** ("Named argument 'style' specifies a parameter for which a positional argument has already been given"); the leading `["flex gap-4"]` IS `style`, so NEVER write `style:` a second time. (b) Putting a named argument *before* a positional one — `view.Box(props: new(){…}, ["card"])` → **CS8323** ("Named argument is used out-of-position but is followed by an unnamed argument"). Because the only positional is the leading style[], naming everything after it makes BOTH impossible. NEVER pass a second positional argument — no positional text, no positional children, no positional click handler; name it. **The ONLY exception is `view.TextField` when binding** (see its bullet): its overloads misroute a positional array, so there you name `style:` too.
- **`Main()` MUST return after `UI.Root(...)`. Do NOT add `await Task.Delay(Timeout.Infinite)` or any other infinite wait at the end of Main().** `UI.Root` registers the reactive renderer and returns immediately; the Ikon server framework keeps the process alive on its own. If Main() blocks forever, `OnServerStartedAsync()` never completes and the server dies with `TimeoutException` after 2 minutes (visible only in logs — the build is clean and the Critic gives the file a 9, but the app never actually starts). The complete Main() body is just `UI.Root([Page.Default], content: view => { … });` followed by closing braces.
- **ASCII quotes ONLY in C# source — never Unicode curly quotes `“` `”` `‘` `’`.** Even inside a `$"..."` interpolated string literal, the C# compiler does not accept smart quotes — CS1002 "expected ;" appears at the curly-quote position because the lexer sees a stray Unicode character, not a string delimiter. Some code editors auto-correct typed `"` into `“` and `”`; do not let that happen in your output. The same rule applies to apostrophes (`'` is C#, `’` is not).
- **A literal double-quote inside an interpolated `$"..."` string MUST be escaped `\"` — an unescaped inner `"` closes the string early and desyncs the parser for the whole rest of the file.** Wanting the text `Add card to "Done"` and writing `$"Add card to "{col}""` ends the string at the first inner quote, leaving `{col}` as loose tokens → a **CS1002 / CS1010 / CS1026** cascade: dozens of phantom "; expected" / ") expected" errors across the file, all from this ONE real mistake. When a single file suddenly shows a burst of those codes, look for an unescaped `"` (or an unbalanced `(`/`{`) — don't try to fix each reported line. Fix by escaping the quotes — `$"Add card to \"{col}\""` — or, simplest, dropping them — `$"Add card to {col}"`. For text with many literal quotes, switch to a raw interpolated string `$"""Add card to "{col}"."""`, where `"` needs no escaping.
- **Raw-string interpolation: match `$` count to brace nesting.** `$"""..."""` (single `$`) treats single `{` as interpolation and `{{` as a literal `{`. `$$"""..."""` (double `$$`) flips it: single `{` is literal and `{{...}}` is interpolation. Writing `$"""...{{animal}}..."""` (single `$` with double-brace interpolation) produces CS9007/CS9008 "raw string literal does not start with enough $ characters". **Default to the simplest form**: if your template has interpolations AND literal `{` / `}` chars (e.g. JSON examples in an LLM prompt), use `$$"""..."""` with `{{x}}` interpolations and single `{` / `}` for the literals. If the template has interpolations but NO literal braces, use plain `$"""..."""` with `{x}`. If the template is just static text, use bare `"""..."""` with no `$`. Never reach for `\n` escape soup in single-line `"..."` strings — raw strings already preserve newlines.
- **TextField's `bind:` is a non-nullable `Reactive<string>`. Don't pass `bind: null` — and don't dodge that with `bind: null!`.** When you don't have a Reactive to bind to, OMIT the `bind:` argument entirely; the value flows through `value:` + `onValueChange:` instead. Passing `bind: null` produces CS8625 ("Cannot convert null literal to non-nullable reference type"); silencing it with the null-forgiving `bind: null!` compiles but is still wrong — `bind` and `value:` are two different modes, so a nulled bind alongside `value:` breaks the input. Pick ONE mode. The full no-bind pattern: `view.TextField(value: _input.Value, onValueChange: async v => { _input.Value = v; }, onSubmit: async _ => …, clearOnSubmit: true)`.
- **`bind:` exists ONLY on `view.TextField` / `view.TextArea`. `view.Select`, `view.Checkbox`, `view.Switch`, `view.Slider`, `view.RadioGroup` do NOT have `bind:`** — passing it is **CS1739**. The state parameter AND the callback both differ by component. `view.Select` / `view.RadioGroup` take a **`string` `value:`** + `onValueChange:`; `view.Slider` takes a **`IReadOnlyList<double>` `value:`** + `onValueChange:`; but `view.Checkbox` / `view.Switch` take a **`bool` `isChecked:`** + `onCheckedChange:` — on those two `value:` is a `string?` form value, NOT the checked state, so passing the bool to `value:` is **CS1503** (`cannot convert 'bool' to 'string?'`). E.g. `view.Select(value: _stage.Value, options: [..], onValueChange: async v => { _stage.Value = v; })`, `view.Checkbox(isChecked: _done.Value, onCheckedChange: async c => { _done.Value = c; })`, and `view.Switch(isChecked: _enabled.Value, onCheckedChange: async e => { _enabled.Value = e; })`. Don't carry the TextField `bind:` prior over to the other inputs. Also for `view.Select`: `options:` is `IReadOnlyList<SelectOption>` where each option carries BOTH value and label — `options: [new SelectOption("won", "Won"), new SelectOption("lost", "Lost")]`. There is NO parallel `labels:` parameter (CS1739) and `options:` is not a `string[]` (CS1503) — don't bring the HTML `<select>` "options + labels arrays" model; one `SelectOption(value, label)` per choice. And `view.Slider` is range/multi-thumb, so its `value:` and `onValueChange` are **list-valued `IReadOnlyList<double>`**, not a scalar: `view.Slider([Slider.Default], value: [(double)_bpm.Value], min: 0, max: 200, onValueChange: async v => { _bpm.Value = (int)v[0]; })`. Scalar `value: _bpm.Value` is CS1503 and `(int)v` is CS0030 — wrap the value in `[...]` and read `v[0]`.
- **Never name a lambda parameter (or local) with a C# reserved keyword — `checked` is the classic trap on `onCheckedChange:`.** The semantically obvious name for the `onCheckedChange:` callback's `bool` is `checked`, but `checked` is a C# keyword, so `onCheckedChange: async checked => { … Done = checked … }` is a **syntax error** — `CS1003 "',' expected"` at the `checked` token, often cascading into CS1525 / CS1026 — NOT an API or style error, even when the line sits right next to a style array (a tempting but wrong thing to blame). Name it `isChecked` (or `c` / `value`): `view.Checkbox(isChecked: _done.Value, onCheckedChange: async isChecked => { _todos.Value[i] = item with { Done = isChecked }; })`. The same applies to every other reserved word used as an identifier — `event`, `params`, `lock`, `default`, `base`, `new`, `object`, `string` — pick a domain name (`evt`, `parameters`, …) instead. **Diagnostic:** a CS1003/CS1525/CS1026 syntax cascade pointing at a `keyword =>` or `keyword)` token is this, not a style or API problem.
- **Overlay `onOpenChange` callbacks hand you a `bool?`, not a `bool`.** `view.Dialog` / `AlertDialog` / `Popover` / `Toast` (and `Select`'s `onOpenChange`) are `Func<bool?, Task>` — the parameter can be null. Branching on it directly is **CS0266** ("cannot convert `bool?` to `bool`"): `onOpenChange: async open => { if (!open) … }` and `open ? a : b` both fail. Coalesce or compare to a literal: `onOpenChange: async open => { _open.Value = open ?? false; }`, or `if (open == false) …` / `if (open == true) …`. (`Reactive<T>.Value` itself is NOT nullable — this is specifically the `onOpenChange` parameter; don't start `?? `-guarding `.Value` reads to chase this error.)
- **`view.Dialog`, `view.AlertDialog`, `view.Link`, `view.Button` accept the natural param shapes — don't hunt for an exact name.** Both overlays take `title:` / `description:` (string convenience) AND a `content:` lambda (full custom body) — use whichever fits: `view.Dialog(open: _open.Value, onOpenChange: async o => _open.Value = o ?? false, title: "Delete entry?", description: "This cannot be undone.", content: v => { /* extra body + buttons */ })`, or `view.AlertDialog(open: _open.Value, onOpenChange: async o => _open.Value = o ?? false, title: "Delete file?", description: "This cannot be undone.", cancelLabel: "Cancel", actionLabel: "Delete", onAction: async () => { await DeleteAsync(); })`. Link and Button both take `text:` OR `label:` for the label string — `view.Link(text: "Open", href: url)` / `view.Link(label: "Open", href: url)` both work, as does a `content:` lambda for rich content. `view.TextField` and `view.TextArea` take a `label:` for a field label rendered above the input — `view.TextField(bind: _name, label: "Name", placeholder: "Jane")` — no need to hand-roll a separate Text + input. (No component takes a React-style `header:` prop; for a fully custom overlay body build it inside `content:` with `Dialog.Header`/`Dialog.Title`/`Dialog.Description` children.)
- **Flat size constants (`.Xs` / `.Sm` / `.Md` / `.Lg`) exist on `Icon` ONLY — `Button.Sm` and `Text.Xs` / `Text.Sm` are CS0117 ("does not contain a definition for 'Sm'").** `view.Icon([Icon.Sm], …)` works, and the LLM over-generalizes that to every style class. It doesn't hold: a BUTTON bakes size into the combined variant constant — `Button.PrimarySm` / `Button.OutlineMd` / `Button.GhostLg` (or the nested `Button.Size.Sm` to compose) — never a bare `Button.Sm`. TEXT uses SEMANTIC constants, not sizes — `Text.Body` / `Text.BodySm` / `Text.Small` / `Text.Caption` / `Text.Label` / `Text.H1`…`Text.H6` — or just a Tailwind size class in the array (`view.Text(["text-xs text-muted-foreground"], …)`); there is no `Text.Xs` / `Text.Sm`. **`view.Icon` has NO `size:` parameter either** — the size is a style-array constant: `view.Icon([Icon.Sm], name: "check")`, NOT `view.Icon(size: …, name: "check")` (which is **CS1739** "no parameter named 'size'", seen 17× in one app). Icon's first positional is the style array (`[Icon.Xs/Sm/Md/Lg]` plus any Tailwind/colour classes); `name:` is the lucide icon name.
- **`view.Button` has NO `variant:` / `color:` / `size:` parameter — the variant AND size are ONE baked style constant in the style array.** The React/shadcn prior `view.Button(variant: "destructive", size: "sm", label: "Delete")` is **CS1739** ("does not have a parameter named 'variant'"). Put the look in the array instead: `view.Button([Button.ErrorMd], label: "Delete", onClick: async () => { … })`. The variant constants are `Button.Primary*` / `Button.Secondary*` / `Button.Outline*` / `Button.Ghost*` / `Button.Error*` (each with a `Sm` / `Md` / `Lg` size suffix, e.g. `Button.PrimaryMd`, `Button.ErrorMd`). **For a destructive / delete button use `Button.ErrorMd` (the filled error style). Outline and error do NOT combine on Button — there is NO `Button.OutlineError*` (CS0117 "does not contain a definition for 'OutlineErrorMd'") and NO `Button.Destructive` / `Button.Danger`.** For an outlined button use `Button.OutlineMd` (neutral); the error tone is filled-only.
- **There is NO `view.Spinner()`-style loading component you need to hand-roll — `view.Spinner()` is built in.** It renders an animated circular loading indicator: `view.Spinner()` (or `view.Spinner(size: SpinnerSize.Lg)`, or `view.Spinner(["text-sky-400"])` to recolour). Use it directly for async/pending states — `if (_loading.Value) { view.Spinner(); }`. (The equivalent hand-rolled form is a `view.Box` with the `Icon.Spinner` style; prefer the typed component.)
- **A conditional style list — `view.X(cond ? [..] : [..], …)` — does NOT compile (CS1503).** A ternary of two collection expressions has no common type (collection expressions are target-typed), so the compiler can't infer `string[]` for the `style` parameter and misbinds the `cond` bool as a positional argument. This bites the most common conditional-styling shapes: dark-mode wrappers, drag-over highlights, active/selected rows. Two fixes: (a) extract a typed local first — `string[] style = isActive ? ["bg-active", "text-primary"] : ["text-muted"]; view.Box(style, content: …);` — or (b) keep ONE array and make the *element* conditional: `view.Box(["rounded p-2", isActive ? "bg-active" : "bg-card"], content: …)`. Form (b) is usually cleaner for toggling a few classes. **A ternary INSIDE one array is FINE and is NOT this pitfall** — `view.Button(label, style: ["flex-1", cond ? "line-through" : "text-foreground", Button.GhostSm])` compiles, because the outer `[...]` target-types every element, including the ternary's two `string` branches and the `const string` `Button.*` constant. Only a ternary whose two branches are *whole arrays* trips this. **Diagnostic:** this pitfall's signature is **CS1503** (an argument binding/type error). It NEVER produces syntax errors — if the build shows **CS1003 / CS1525 / CS1026** at or near a style array, the cause is something else on that line (an unescaped quote, an unbalanced brace/paren, or a reserved word used as an identifier — see the `checked` pitfall), NOT the style list. Don't "fix" a valid in-array ternary to chase a syntax error.
- **`IApp` is a generic interface — ALWAYS pass type arguments, and declare the two records `public`.** The canonical app class shape is `[App] public class MyApp(IApp<SessionIdentity, ClientParameters> app)` with `public record SessionIdentity(string UserId)` and `public record ClientParameters(string Name = "Anonymous")` (use empty `()` if you have no fields). Two failure modes: (1) writing the primary-constructor param as bare `IApp app` (no type args) produces CS0305 "requires 2 type arguments"; (2) declaring the records WITHOUT `public` (`record SessionIdentity(...)`) makes them `internal` by default — but the app class is `public`, so the constructor's `IApp<…>` type argument becomes less accessible than the constructor → **CS0051 "Inconsistent accessibility"**. BOTH records must be `public record`. The scaffold's existing app file already has the canonical `public record` shape — preserve it; don't rewrite the records or the constructor signature from scratch (rewriting from memory is exactly how the `public` modifier gets dropped).
- **Interactive elements need findable handles — `label:`, `placeholder:`, `key:`.** Two reasons: real users with assistive tech, and (when `--validate-app` is set) the AppValidator's browser subthread that drives the running app by clicking marked elements by their role + accessible name. A bare `view.TextField(bind: _search)` is invisible to the validator's element marks; write `view.TextField(bind: _search, label: "Search", placeholder: "Type to filter…")` instead — the same field becomes findable by both screen readers and the validator. Dynamic lists need `key:` on each rendered row so reorders/deletes don't confuse element marking. Buttons get a clear label as their first positional string (`view.Button("Add")`). Sliders are genuinely hard for an LLM-driven browser to drag — if a slider's value matters, pair it with labeled `+`/`-` buttons or a discrete value picker the validator can click reliably.
- **Clickable element? Use `view.Button` — never `view.Box` with `onClick:`.** It's tempting for custom-looking buttons (calculator digits, vote tiles, card actions) to reach for `view.Box([…styling], onClick: async () => …, content: v => v.Text("1"))` because the Box gives full styling control. The trap: a Box renders as a plain `<div>` with no `role="button"` and no accessible name, so screen readers don't announce it AND the AppValidator's element marking won't list it as interactive — the validator can't click it. Use `view.Button("1", [...styling], onClick: …)` instead; Button accepts the full style array and supports the same custom looks (`Button.GhostMd` for no chrome, full Tailwind for fully custom). Same rule for clickable links — `view.Link(text: "…", href: "…")` or `view.Button` with router behavior; never a plain Box with onClick.
- **Lifecycle events: use the `app.OnStarting(...)` / `app.OnClientJoined(...)` extension helpers.** The raw events (`app.StartingAsync`, `app.ClientJoinedAsync`, etc) take an `AsyncEventHandler<TEventArgs>` delegate — a single-arg `Func<TEventArgs, Task>`. The .NET / standard event-handler prior `(sender, args) => ...` does NOT match (CS1593), and zero-arg lambdas `() => ...` ALSO don't match. The friendly extensions take the LLM-natural shape directly: `app.OnStarting(async () => await InitDbAsync())`, `app.OnStopping(async () => await CleanupAsync())`, `app.OnClientJoined(async ctx => ...)` (receives `Context` directly — `ctx.SessionId`, `ctx.UserId`, also `ctx.ClientSessionId` as a same-thing alias), `app.OnClientJoined(async (ctx, parameters) => ...)` (typed-parameters overload — receives the joining client's `TClientParameters` directly, e.g. `parameters.Name`, no `app.Clients[...]!.Parameters` drill needed), `app.OnClientLeft(async ctx => ...)` / `app.OnClientLeft(async (ctx, parameters) => ...)`, `app.OnMessageReceived(async msg => ...)`. The event-args wrapper types (`StartingEventArgs`, `ClientJoinedEventArgs`, etc) exist but the extensions skip them. Don't invent `AppStartingEventArgs` / `AppStoppingEventArgs` — those types don't exist; the canonical names omit the `App` prefix.
- **`using` directives MUST come before the top-level `return await App.Run(args);` statement — CS1529.** `return await App.Run(args);` is the program's first *statement*, but C# requires every `using` directive to precede ALL statements and type declarations in the file. So if the app file needs any local `using` (e.g. `using System.Collections.Concurrent;`, or a generated protocol namespace like `using MyApp.Protocol;`), those usings go ABOVE `return await App.Run(args);`, never below it. Putting `App.Run` on line 1 and a `using` under it is **CS1529 "A using clause must precede all other elements"** — and deleting the entry-point line to "fix" it instead yields **CS5001 "Program does not contain a static 'Main'"** (you removed the entry point). Correct order: `using …;` lines first → blank line → `return await App.Run(args);` → records/`[App]` class. Better still, prefer adding shared namespaces to `GlobalUsings.cs` so the app file needs no local usings at all. Wherever this doc says App.Run goes "at the top of the file", it means the first *statement*, after any usings.
